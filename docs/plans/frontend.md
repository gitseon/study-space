# 프론트엔드 문제은행 구현 계획

작성일: 2026-10-09. 상태: 계획 확정, 구현 전.

## 1. 확정된 결정

- 회차: 프론트엔드 3회. 회차마다 객관식 21, 단답형 9, 서술형 2로 동일하게 구성한다. 월평형 구현 회차는 만들지 않는다.
- 코드 들여쓰기: HTML, CSS, JavaScript 모두 2칸. 기존 Java의 4칸 기준과 다르므로 QUESTION_AUTHORING.md에 예외로 적는다.
- 홈 화면 트랙 이름: 프론트엔드.
- 출제 범위 원본: `source/frontend.txt`의 7개 대주제와 세부 주제.
- 제작 지침 원본: `requirements.md`와 QUESTION_AUTHORING.md.

## 3. 막히는 지점

1. `scripts/validate_questions.py`가 회차 구성과 주제 coverage를 알고리즘 scope 하나로 고정한다.
2. `scripts/audit_bias.py`가 모든 회차를 한 bank로 묶어 63문항 기준을 적용한다.
3. `assets/quiz.js`의 주제별 연습이 `subject-01~03`만 불러오고, 합친 정답 순서에 연속·반복 검사가 없다.
4. `assets/app.js`의 주제 버튼이 `subject-01`로 고정되어 있다.
5. AGENTS.md의 범위 문장과 코드 표준이 알고리즘과 Java 기준이다.

## 4. 단계별 계획

### 단계 0. 기준 문서

- AGENTS.md에 트랙 개념을 추가한다. 알고리즘 기준은 그대로 둔다.
- QUESTION_AUTHORING.md에 프론트엔드 절을 추가한다.
  - 코드 형식: 2칸 들여쓰기, 세미콜론, 작은따옴표, 중괄호 필수.
  - 코드 줄 길이 상한: 360px 화면에서 측정해 확정한다. 40자 안팎으로 예상한다.
  - 브라우저나 버전에 따라 결과가 달라지는 동작은 출제하지 않는다.
  - 정답이 둘이 될 표현을 피한다. Falsy 값은 명세상 8가지(`0n`, `-0` 포함)이므로 개수를 묻지 않고 판별을 묻는다.
- `source/scope-frontend.json`을 만든다. 7개 대주제(버튼 단위), 세부 태그, 회차별 출제표를 담는다.

### 단계 1. 파이프라인 일반화

- `exam.json`에 `track` 필드를 둔다. 값이 없으면 `algorithm`으로 간주한다. 기존 exam.json은 수정하지 않아 contentVersion과 저장된 응시 기록을 보존한다.
- `validate_questions.py`는 구성 수, coverage, 출제표를 트랙별 scope에서 읽는다.
- `audit_bias.py`는 bank 집계를 트랙별로 나눈다. 주제별 연습 세트의 정답 순서 검사를 추가한다.
- manifest에 트랙별 topics와 회차 목록을 넣는다.
- 회귀 기준: 기존 알고리즘 `data/*.json`의 diff가 0이고 편향 보고서 수치가 이전과 같다.
- `tests/content`에 트랙 분리, 주제 세트, 줄 길이 검사 테스트를 추가한다.

### 단계 2. 화면

- 홈에 트랙 탭(자료구조와 알고리즘, 프론트엔드)을 둔다. 문제집 카드와 주제 버튼은 선택한 트랙을 따른다.
- 주제 버튼에 문항 수를 표시한다. `topicExam`은 manifest에서 트랙의 회차를 불러온다.
- 코드 스니펫: 언어 라벨(HTML, CSS, JS), CDN 없는 가벼운 구문 강조(escape 후 토큰 적용), 모바일 글자 크기 조정, 줄 길이 기준 초과 시에만 가로 스크롤.
- E2E: 360px 화면에서 모든 프론트엔드 스니펫의 `scrollWidth <= clientWidth`를 검사한다.

### 단계 3. 1회차 시범 제작 (32문항) 후 검토

- `source/frontend-01/`에 exam.json, questions.md, solutions.md를 만든다.
- `scripts/verify_frontend_answers.mjs`로 정답을 실제 실행해 확인한다.
  - JS 출력, Promise 순서, `splice`, 스프레드 복사는 Node로 실행한다.
  - 명시도, 마진 병합, sticky, DOM 삽입 위치, classList는 Playwright Chromium에서 렌더링해 측정한다.
  - 결과는 `reports/frontend-verification.json`에 남긴다.
- 해설은 정답 근거, 풀이 과정, 오답별 이유, 흔한 실수 순서로 쓴다.
- 1회차 완성 후 화면과 문항 품질을 확인받고 이어서 진행한다.

### 단계 4. 2회차와 3회차

- 1회 개념과 기본 추적, 2회 경계 조건과 오류 분석, 3회 응용과 복합 판단. 숫자만 바꾼 중복 문제는 만들지 않는다.
- 3회 합계 63문항의 객관식 정답은 번호별 14~18개로 맞춘다.
- 서술형은 회차마다 사례를 바꾼다.

### 단계 5. 완료 증거

- README의 검증 명령 전체와 새 검증 스크립트를 실행하고 `check.yml`에 추가한다.
- PR 본문에 범위와 문항 수, 정답 분포, 최대 연속 길이, 길이 편향 검토, 정답과 해설 검수 결과를 적는다.

## 5. 회차별 출제표 (과평 21/9/2 동일)

| 대주제 | 객관식 | 단답형 |
| --- | ---: | ---: |
| HTML 기본과 시맨틱 웹 | 3 | 1 |
| CSS 레이아웃과 선택자 | 4 | 2 |
| JavaScript 핵심 문법과 데이터 타입 | 4 | 2 |
| 함수와 this 바인딩 | 2 | 1 |
| DOM과 BOM 제어 | 3 | 1 |
| 비동기 통신과 Promise | 3 | 1 |
| 웹 스토리지와 네트워크 데이터 전송 | 2 | 1 |
| 합계 | 21 | 9 |

- 서술형 2문항은 회차마다 다른 사례로 낸다. 후보: 마진 병합과 명시도 설명, Promise 체이닝과 catch 이후 흐름, 일반 함수와 화살표 함수의 this 차이, localStorage와 sessionStorage 비교, GET과 POST 비교.
- 세부 태그 약 25개는 3회를 합쳐 모두 한 번 이상 나오도록 검사한다.
- 단답형은 문항별 허용 표기와 정규화 규칙을 지정한다. 코드 출력은 대소문자와 공백이 의미를 가지므로 `none` 또는 `trim`을 쓴다.
- 난이도 제안은 기존과 같이 쉬움 10, 보통 16, 어려움 6이다.

## 6. 위험과 주의

- 기존 알고리즘 결과가 바뀌면 안 된다. 단계 1의 회귀 기준으로 확인한다.
- 일부 동작은 문서에 따라 다르게 서술된다. 실제 실행으로 확인되지 않은 항목은 출제하지 않는다.
- `git`에서 "dubious ownership" 오류가 나므로 커밋 전에 `git config --global --add safe.directory E:/GISEON/study-space`가 필요하다.

## 7. 구현 결과와 계획과의 차이

구현 완료일: 2026-10-10. 단계 0부터 5까지 진행했고 커밋과 PR 생성은 하지 않았다.

- 세부 주제 태그는 28개다. 계획의 약 25개는 원문 항목을 세분화하면서 늘었다. 3회를 합쳐 모든 태그가 한 번 이상 나오는지 `validate_questions.py`가 검사한다.
- 코드 한 줄의 상한은 계획의 42자에서 38자로 낮췄다. 360px 화면에서 코드 상자 안쪽 폭이 약 252px이고 Consolas가 없는 환경의 고정폭 글꼴은 글자당 약 6.6px이라 42자는 일부 환경에서 넘친다.
- 실행 검증은 `scripts/verify_frontend_answers.mjs`와 `scripts/frontend_checks.mjs`, `scripts/frontend_checks_02_03.mjs`로 구현했다. 96문항 중 73문항은 코드를 실제로 실행하고 23문항은 `source/frontend-reviews.json`의 재풀이 기록으로 확인한다.
- 주제별 연습 세트의 정답 순서 검사를 알고리즘 트랙에도 적용했다. 그 결과 이진 탐색 세트가 같은 번호 3연속이라는 기존 문제가 드러나 `subject-01-q18`과 `subject-01-q20`의 선지 순서를 바꾸고 revision을 올렸다.
- 홈 화면 주제 버튼에는 문항 수를 표시한다. 문항 수는 객관식과 단답형과 서술형을 합친 값이다.
