# DB 개념 요약 노트

DB 강의 16권의 개념을 다시 설명한 복습 노트이다. SQL은 MySQL 8.4와 InnoDB를 기준으로 읽되, 실제 시험 환경이 다르면 해당 버전의 동작을 먼저 확인한다. 강의의 예제나 확인문제를 옮기지 않고 작은 새 예제로 원리를 설명한다. 실제 시험의 출제 범위나 비중을 보장하지 않는다.

백엔드와 함께 볼 때는 요청 처리와 MVC를 먼저 복습한 뒤 Part 10의 JDBC로 연결한다. 각 Part의 복습 질문은 먼저 답을 생각하고 `답 보기`로 확인한다.

## Part 1. DB와 SQL의 기본

### 1. 저장소와 관리 시스템

데이터베이스는 관련 데이터를 조직해 저장한 집합이고 DBMS는 저장, 검색, 갱신, 권한과 동시 접근을 관리하는 소프트웨어이다. MySQL Server가 DBMS이며 Workbench는 서버에 접속하는 클라이언트 도구다. Workbench를 닫는 것과 서버를 종료하는 것은 다르다.

관계형 모델은 데이터를 테이블로 표현하고 키와 제약조건으로 관계를 관리한다. 행은 한 대상을 표현하고 열은 그 대상의 속성을 표현한다. 테이블에 저장된 순서는 조회 결과의 순서를 보장하지 않는다.

| 용어 | 이해할 기준 |
| --- | --- |
| 스키마 | 테이블과 제약 등 데이터 구조의 정의. MySQL에서는 DATABASE와 SCHEMA가 같은 의미로 사용됨 |
| 행과 열 | 행은 레코드, 열은 속성에 대응 |
| 기본키 | 행을 유일하게 식별하며 NULL을 허용하지 않음 |
| 외래키 | 다른 키를 참조해 테이블 사이의 참조 무결성을 유지 |
| 트랜잭션 | 여러 변경을 하나의 논리적 작업 단위로 묶음 |

### 2. SQL 명령의 역할

| 구분 | 목적 | 대표 명령 |
| --- | --- | --- |
| DDL | 구조 정의 | CREATE, ALTER, DROP, TRUNCATE |
| DML | 데이터 조회·변경 | SELECT, INSERT, UPDATE, DELETE |
| DCL | 접근 권한 제어 | GRANT, REVOKE |
| TCL | 트랜잭션 제어 | COMMIT, ROLLBACK, SAVEPOINT |

SELECT를 DQL로 따로 분류하는 설명도 있다. 분류 이름보다 실제로 무엇을 바꾸고 어떤 결과를 내는지 구분한다. `USE`는 사용할 데이터베이스를 선택한다. `SHOW TABLES`, `DESCRIBE`, `SHOW CREATE TABLE`은 구조를 확인할 때 유용하다.

### 3. 접속 환경과 권한

- 접속에는 서버 주소, 포트, 계정, 데이터베이스가 필요하다. 계정은 MySQL에서 사용자 이름과 접속 호스트의 조합으로 구분된다.
- 애플리케이션에는 필요한 권한만 부여한다. 모든 코드에서 관리자 계정을 쓰는 방식으로 연습 예제를 일반화하지 않는다.
- `utf8mb4`는 문자 저장 방식이고 collation은 비교와 정렬 규칙이다. 같은 문자열도 대소문자·악센트 구분 설정에 따라 비교 결과가 달라질 수 있다.
- Workbench의 Safe Updates는 위험한 변경을 줄이는 보조 설정이다. WHERE가 없는 UPDATE·DELETE의 의미를 바꾸는 SQL 규칙은 아니다.

   답: 연결된 MySQL Server이다. Workbench는 SQL을 전달하고 결과를 보여 주는 클라이언트다.
2. 기본키를 따라 입력했으면 SELECT 결과도 그 순서대로 보장되는가?
   답: 아니다. 결과 순서를 보장하려면 ORDER BY를 지정한다.

## Part 2. SELECT, 조건, NULL과 정렬

### 1. 구문 순서와 논리적 해석 순서

```sql
SELECT category, COUNT(*) AS n
FROM item
WHERE price >= 40
GROUP BY category
HAVING COUNT(*) >= 2
ORDER BY n DESC, category ASC
LIMIT 3;
```

읽는 순서는 FROM에서 대상을 정하고 WHERE로 행을 거른 뒤 GROUP BY로 묶는 것이다. HAVING으로 그룹을 거르고 SELECT의 값을 만든 후 ORDER BY와 LIMIT을 적용한다고 이해한다. 실제 물리 실행 계획은 옵티마이저가 달리 정할 수 있다.

- SELECT만으로 상수나 함수를 계산할 수 있으므로 MySQL의 모든 SELECT에 FROM이 필수인 것은 아니다.
- SELECT에서 만든 별칭을 같은 단계보다 앞선 WHERE에서 바로 참조하지 않는다. MySQL은 ORDER BY나 HAVING에서 별칭 사용을 허용한다.
- DISTINCT는 선택한 열 조합이 같은 결과 행의 중복을 제거한다.
- `BETWEEN a AND b`는 양 끝을 포함한다. 시간 값은 종료일 자정 누락을 피하도록 시작 이상·다음 경계 미만 조건을 고려한다.
- `LIKE 'a%'`의 `%`는 길이 0 이상, `_`는 한 문자에 대응한다. 비교의 대소문자 구분은 collation을 확인한다.
- AND는 OR보다 먼저 평가되므로 의도한 묶음을 괄호로 표현한다.

### 2. NULL은 값이 없거나 알 수 없다는 표시

`NULL = NULL`은 참이 아니다. 일반 비교에 NULL이 섞이면 UNKNOWN이 될 수 있고 WHERE는 TRUE인 행만 남긴다. NULL을 찾을 때는 `IS NULL`을 쓴다.

| 식 | 결과 |
| --- | --- |
| `NULL = 3` | UNKNOWN |
| `NULL IS NULL` | TRUE |
| `FALSE AND UNKNOWN` | FALSE |
| `TRUE AND UNKNOWN` | UNKNOWN |
| `TRUE OR UNKNOWN` | TRUE |
| `FALSE OR UNKNOWN` | UNKNOWN |
| `NOT UNKNOWN` | UNKNOWN |

MySQL의 `<=>`는 NULL을 포함해 비교하는 별도 연산자이다. 일반 `=`와 혼동하지 않는다. `IS NULL`을 사용하면 의도가 더 분명한 경우가 많다.

### 3. 작은 데이터로 추적하기

다음 item 데이터는 이 노트의 조회·집계 예제에서 공통으로 사용한다.

| id | category | price |
| --- | --- | ---: |
| 1 | book | 40 |
| 2 | book | 60 |
| 3 | pen | NULL |
| 4 | pen | 20 |

앞의 쿼리는 가격이 40 이상인 1·2번 행을 남긴다. book 그룹의 개수는 2라 HAVING을 통과한다. 최종 결과는 `book, 2` 한 행이다. NULL 가격은 WHERE 비교에서 TRUE가 아니므로 제외된다.

`ORDER BY price DESC, id ASC`처럼 동점일 때의 기준도 적어야 LIMIT으로 특정 행을 확정할 수 있다. `LIMIT 2 OFFSET 1`은 정렬된 결과에서 첫 행을 건너뛰고 최대 두 행을 가져온다.

### 자주 틀리는 포인트

- NULL을 0이나 빈 문자열과 같은 값으로 본다.
- `DISTINCT category, price`가 category만 중복 제거한다고 생각한다.
- ORDER BY 없이 우연히 보인 순서를 정답으로 쓴다.

### 복습 질문

1. `price <> 40`은 price가 NULL인 행을 포함하는가?
   답: 포함하지 않는다. NULL과의 일반 비교는 UNKNOWN이고 WHERE는 TRUE만 남긴다.
2. LIMIT으로 상위 두 행을 확정하려면 무엇을 확인해야 하는가?
   답: ORDER BY와 동점일 때의 추가 정렬 기준이 있어야 한다.

## Part 3. 함수, 집계, GROUP BY와 HAVING

### 1. 단일 행 함수

| 분류 | 함수 | 구분할 점 |
| --- | --- | --- |
| 숫자 | ABS, ROUND, TRUNCATE, CEIL, FLOOR | TRUNCATE는 자릿수 뒤를 버리고 FLOOR는 작은 쪽 정수로 내림 |
| 문자열 | CONCAT, SUBSTRING, REPLACE, TRIM | SUBSTRING의 일반적인 양수 시작 위치는 1부터 계산 |
| 길이 | LENGTH, CHAR_LENGTH | 앞은 바이트 수, 뒤는 문자 수 |
| 날짜 | DATE_ADD, DATE_SUB, DATE_FORMAT | 날짜 연산과 출력 문자열 형식 변환을 구별 |
| 차이 | DATEDIFF, TIMESTAMPDIFF | DATEDIFF는 앞 날짜에서 뒤 날짜를 뺌. TIMESTAMPDIFF는 끝에서 시작을 뺀 단위 차이 |
| 변환 | CAST, CONVERT | 암묵적 형 변환에 기대기보다 원하는 자료형을 표현 |
| 조건 | CASE, IF, IFNULL, NULLIF | IFNULL은 NULL 대체, NULLIF는 두 값이 같으면 NULL |

`TRUNCATE(-2.8, 0)`은 -2이고 `FLOOR(-2.8)`은 -3이다. `TRUNCATE()` 함수와 `TRUNCATE TABLE` 명령은 전혀 다른 기능이다. 소수 계산 문항은 정수·DECIMAL·부동소수점 중 어떤 타입을 쓰는지 확인한다.

`DATEDIFF('2026-03-08', '2026-03-05')`는 3이다. 같은 날짜를 시작·끝 순서로 `TIMESTAMPDIFF(DAY, '2026-03-05', '2026-03-08')`에 주면 역시 3이다. 현재 시각을 쓰는 함수는 실행 날짜나 시간대에 따라 값이 바뀌므로 출력 문제에서는 고정 시각을 사용한다.

### 2. 집계에서 NULL 처리

Part 2의 네 행에서 `COUNT(*)`는 4, `COUNT(price)`는 3이다. `SUM(price)`는 120이고 `AVG(price)`는 40이다. NULL을 0으로 바꾼 뒤 평균 내면 120을 4로 나눈 30이므로 다른 질문에 답하게 된다.

| 표현 | 세는 대상 |
| --- | --- |
| `COUNT(*)` | 행의 수 |
| `COUNT(price)` | price가 NULL이 아닌 행 |
| `COUNT(DISTINCT category)` | NULL을 제외한 서로 다른 category 값 |
| `SUM(price)`, `AVG(price)` | NULL이 아닌 price 값으로 계산 |

조건에 맞는 행이 없는 전체 집계에서는 COUNT는 0, SUM과 AVG는 NULL이다. GROUP BY가 있는 쿼리는 입력이 비면 그룹 자체가 없을 수도 있다.

### 3. 행 조건과 그룹 조건

WHERE는 집계 전의 개별 행을 거르고 HAVING은 그룹을 거른다. SELECT에 집계하지 않은 열을 쓸 때는 GROUP BY의 열 또는 그 열로 값이 결정되는 관계인지 확인한다. MySQL의 `ONLY_FULL_GROUP_BY`는 이런 불확정 결과를 검사한다. 초보 예제는 비집계 열을 GROUP BY에 명시해 읽기 쉽게 쓴다.

```sql
SELECT category, SUM(price) AS total
FROM item
GROUP BY category
HAVING SUM(price) >= 80
ORDER BY category;
```

book 합계는 100이고 pen 합계는 20이므로 결과는 `book, 100`이다.

### 4. 소계와 조건부 집계

`WITH ROLLUP`은 GROUP BY 결과에 소계와 총계를 추가한다. 추가된 합계 행의 NULL과 원래 데이터의 NULL은 다르다. `GROUPING(열)`로 합계 때문에 생긴 NULL인지 판별한다.

조건부 집계는 `SUM(CASE WHEN 조건 THEN 값 ELSE 0 END)`처럼 원하는 범주에 해당하는 값을 더한다. 이를 이용해 행에 있던 범주를 열로 펼치는 피벗 형태를 만들 수 있다. `COUNT(CASE WHEN 조건 THEN 1 END)`는 조건에 맞지 않는 행이 NULL이 되므로 해당 행만 센다. ELSE 0을 붙이면 0도 NULL이 아니어서 모두 세는 실수를 주의한다.

### 복습 질문

1. 값이 10, NULL, 20일 때 COUNT와 AVG는 어떻게 다른가?
   답: COUNT(*)는 3, COUNT(값)은 2이고 AVG(값)은 15이다. NULL은 평균의 분모에서도 제외한다.
2. 원래 데이터의 NULL 그룹과 ROLLUP 총계 행을 어떻게 구분하는가?
   답: GROUPING 함수로 합계 처리 때문에 생긴 NULL인지 확인한다.

## Part 4. JOIN과 집합 연산

### 1. 조인을 두 관점으로 구분하기

INNER·OUTER는 어떤 행을 남길지의 구분이고 EQUI·NON-EQUI는 어떤 비교 조건으로 연결할지의 구분이다. SELF JOIN은 같은 테이블을 다른 별칭으로 다시 사용하는 방식이다.

| 방식 | 결과 |
| --- | --- |
| INNER JOIN | 조건을 만족하는 행의 조합만 남음 |
| LEFT JOIN | 왼쪽 행을 보존하고 오른쪽 매칭이 없으면 오른쪽 열이 NULL |
| RIGHT JOIN | 오른쪽 행을 보존. 순서를 바꾸어 LEFT JOIN으로 표현 가능 |
| CROSS JOIN | 두 테이블의 모든 행 조합 |
| SELF JOIN | 직원과 관리자처럼 같은 테이블의 서로 다른 역할을 연결 |
| NATURAL JOIN | 이름이 같은 열들을 암묵적으로 비교하므로 스키마 변경에 주의 |

USING은 두 테이블의 이름이 같은 조인 열을 명시할 때 사용한다. 연결 열이나 조건이 복잡하면 ON으로 쓰는 편이 의도를 드러내기 쉽다. 조인에서 한 행이 여러 행과 매칭되면 결과 행이 늘어난다. 조인은 중복 제거 기능이 아니다.

### 2. 외부 조인에서 ON과 WHERE

두 테이블에 다음 데이터가 있다고 하자.

| member.id | member.name |
| --- | --- |
| 1 | 민 |
| 2 | 유 |

| booking.id | booking.member_id | booking.status |
| --- | --- | --- |
| 10 | 1 | paid |
| 11 | 1 | pending |

```sql
SELECT m.id, b.id AS booking_id
FROM member AS m
LEFT JOIN booking AS b
    ON b.member_id = m.id
    AND b.status = 'paid'
ORDER BY m.id, b.id;
```

결과는 `(1, 10)`, `(2, NULL)`이다. 유료 예약이 없는 회원도 남긴다. `b.status = 'paid'`를 WHERE로 옮기면 미매칭 행의 NULL이 조건을 통과하지 못해 `(1, 10)`만 남는다.

회원별 예약 수를 셀 때 미매칭 회원까지 세는 `COUNT(*)`와 실제 예약의 키만 세는 `COUNT(b.id)`를 구분한다. 위 조건으로 집계하면 2번 회원의 실제 유료 예약 수는 0이다.

### 3. 집합 연산

| 연산 | 의미 |
| --- | --- |
| UNION | 두 결과를 합치고 중복 행 제거 |
| UNION ALL | 두 결과를 합치고 중복 유지 |
| INTERSECT | 양쪽에 있는 공통 행 |
| EXCEPT | 왼쪽에만 있는 행 |

대응하는 SELECT는 열 수가 같고 위치별 데이터 타입이 호환되어야 한다. 별칭이 같은 열을 이름으로 찾아 연결하는 연산이 아니다. MySQL 8.4는 위 연산을 지원하며 교집합·차집합의 지원 여부를 구형 MySQL 지식으로 단정하지 않는다.

MySQL 8.4에는 FULL OUTER JOIN 구문이 없다. 왼쪽 전체와 오른쪽의 미매칭 행을 합치는 방식으로 표현할 수 있지만, 중복까지 보존해야 하는 문제에서 무조건 UNION으로 해결하면 결과가 달라질 수 있다.

### 복습 질문

1. 왼쪽 행이 3개이고 오른쪽 행이 2개인 CROSS JOIN의 행 수는?
   답: 6개이다. 각 왼쪽 행이 모든 오른쪽 행과 연결된다.
2. 매칭되지 않은 회원까지 남기려면 오른쪽 테이블 조건을 어디에 두는지 왜 중요한가?
   답: ON은 매칭 대상을 정하지만 WHERE는 외부 조인 후 만들어진 NULL 행까지 거르기 때문이다.

## Part 5. 서브쿼리와 VIEW

### 1. 결과 모양과 외부 참조

| 구분 | 핵심 |
| --- | --- |
| 스칼라 서브쿼리 | 한 열의 최대 한 행을 값으로 사용. 0행이면 NULL, 여러 행이면 오류 |
| 다중 행 서브쿼리 | IN, ANY, ALL 등 결과 집합에 맞는 연산자 필요 |
| 다중 열 서브쿼리 | 행 값의 각 위치를 대응해 비교 |
| 파생 테이블 | FROM이나 JOIN 위치의 결과를 테이블처럼 사용하며 별칭 부여 |
| 상관 서브쿼리 | 바깥 쿼리의 열을 참조하므로 독립적인 값으로 해석할 수 없음 |

상관 쿼리는 바깥 행마다 참조값이 달라진다고 논리적으로 이해한다. 물리적으로 항상 같은 횟수만큼 반복 실행된다고 단정하지 않는다. 옵티마이저가 다른 형태로 바꿀 수 있다.

```sql
SELECT id, price
FROM item
WHERE price > (
    SELECT AVG(price)
    FROM item
)
ORDER BY id;
```

Part 2 데이터의 평균 가격은 40이므로 결과는 `(2, 60)`이다. 평균을 계산하는 안쪽 쿼리는 바깥 행을 참조하지 않는 비상관 서브쿼리다.

### 2. IN, ANY, ALL, EXISTS

| 표현 | 해석 |
| --- | --- |
| `x IN (서브쿼리)` | 반환값 중 같은 값이 있는지 비교 |
| `x > ANY (서브쿼리)` | 비교 중 하나라도 TRUE인지 검사 |
| `x > ALL (서브쿼리)` | 모든 비교가 TRUE인지 검사 |
| `EXISTS (서브쿼리)` | 결과 행이 한 개 이상 존재하는지 검사 |

NULL 없는 비어 있지 않은 집합에서 `> ANY`는 최솟값 초과, `> ALL`은 최댓값 초과로 이해할 수 있다. 빈 집합이나 NULL이 있으면 이 단순 치환을 적용하지 않는다. 빈 집합에 대한 ANY는 FALSE이고 ALL은 TRUE다.

`NOT IN (2, NULL)`에서 x가 5이면 비교가 UNKNOWN이 되어 WHERE를 통과하지 못한다. 미존재 행을 찾을 때는 NULL 조건을 분명히 하거나 의도에 맞는 NOT EXISTS를 쓴다. 둘의 의미가 모든 상황에서 무조건 같다는 뜻은 아니다.

EXISTS는 SELECT한 값 자체가 아니라 행의 존재를 본다. NULL 값을 가진 행도 존재하는 행이다.

### 3. 뷰

뷰는 SELECT 정의에 이름을 붙여 테이블처럼 조회하는 객체다. MySQL의 일반 뷰를 결과 행이 별도로 영구 저장되는 복사본으로 이해하지 않는다. 자주 쓰는 조회를 감추거나 권한을 분리하는 데 활용한다.

- 단순 뷰는 수정 가능할 수 있지만 집계, GROUP BY, DISTINCT 등이 있으면 수정 가능성이 제한된다.
- `WITH CHECK OPTION`은 뷰를 통해 수정·삽입한 행이 뷰의 조건을 만족하도록 제한한다.
- 뷰가 있다고 원본 테이블 접근이 자동으로 차단되는 것은 아니다. 실제 권한 설정을 확인한다.
- 서브쿼리와 JOIN 중 무엇이 빠른지는 조건과 실행 계획으로 판단한다.

### 복습 질문

1. 스칼라 서브쿼리가 두 행을 돌려주면 첫 행을 쓰는가?
   답: 아니다. 스칼라 위치에서 여러 행을 반환하면 오류가 난다.
2. NOT IN의 결과 집합에 NULL이 섞일 때 무엇을 주의해야 하는가?
   답: 같은 값이 없더라도 비교가 UNKNOWN이 되어 의도한 행이 제외될 수 있다.

## Part 6. DDL, 자료형, 제약조건과 DML

### 1. 구조를 만들 때의 선택

| 항목 | 기준 |
| --- | --- |
| 정수형 | 범위와 부호 여부를 데이터에 맞게 선택 |
| DECIMAL | 정해진 자리수의 정확한 소수 표현. 금액 계산 등에서 고려 |
| FLOAT·DOUBLE | 근삿값 표현. 비교·반올림을 정확한 소수처럼 가정하지 않음 |
| CHAR·VARCHAR | 고정 길이와 가변 길이 문자열. 길이와 인코딩, 비교 규칙을 함께 고려 |
| DATE·DATETIME·TIMESTAMP | 날짜만 필요한지 시각이 필요한지 구분. TIMESTAMP의 시간대 변환에 주의 |

DEFAULT는 값을 생략했을 때 사용할 기본값이다. 명시적으로 준 NULL이 언제나 DEFAULT로 바뀐다고 생각하지 않는다. AUTO_INCREMENT의 번호는 삭제·롤백·동시성으로 빈 값이 생길 수 있으므로 연속된 순번을 보장하지 않는다.

### 2. 제약조건

| 제약 | 역할 |
| --- | --- |
| PRIMARY KEY | 유일하고 NULL이 아닌 식별자. 복합키 가능 |
| UNIQUE | 중복 제한. MySQL은 NULL을 허용한 열에서 여러 NULL 허용 |
| NOT NULL | NULL 금지 |
| CHECK | 조건식이 FALSE가 되는 변경 거부. NULL 금지는 NOT NULL과 별도로 설계 |
| FOREIGN KEY | 참조 대상과의 무결성 확인 |

외래키라고 항상 NULL이 금지되거나 값이 유일해지는 것은 아니다. 참조 관계의 필수 여부와 개수는 NOT NULL, UNIQUE 등과 함께 정한다.

부모 변경에 대해 RESTRICT는 위반을 막고 CASCADE는 연결된 자식에 변경을 전파한다. SET NULL을 사용하려면 자식 열이 NULL을 허용해야 한다. 복합 외래키와 자료형·인덱스 조건은 실제 엔진 기준으로 검토한다.

```sql
CREATE TABLE item (
    id INT PRIMARY KEY,
    category VARCHAR(20) NOT NULL,
    price DECIMAL(8, 2),
    CHECK (price >= 0)
);
```

이 정의는 Part 2 데이터를 저장할 수 있다. price의 NULL은 허용한다. 알 수 없는 가격도 금지하려면 price에 NOT NULL을 추가해야 한다.

### 3. 변경 명령과 복사

INSERT는 열 목록을 명시해 열 순서 변화에 덜 의존하도록 쓴다. UPDATE·DELETE에 WHERE가 없으면 모든 행이 대상이다. 변경 전에 같은 조건의 SELECT로 대상을 확인하는 습관을 들인다.

| 명령 | 남는 것과 주의점 |
| --- | --- |
| DELETE | 조건에 맞는 행 제거. InnoDB의 미커밋 변경은 롤백 가능 |
| TRUNCATE TABLE | 모든 행을 비우는 DDL. MySQL에서 암묵적 커밋을 일으키며 일반 ROLLBACK으로 복구 불가 |
| DROP TABLE | 테이블 객체 자체 제거 |
| CREATE TABLE LIKE | 구조 복사. 데이터와 외래키까지 전부 복제되는 것은 아님 |
| CREATE TABLE AS SELECT | 조회 결과로 생성. 기존 PK·인덱스까지 자동 보존되는 것은 아님 |

`INSERT ... ON DUPLICATE KEY UPDATE`는 PRIMARY KEY 또는 UNIQUE 충돌 시 지정한 갱신을 수행한다. 단순히 같은 내용의 행이 있으면 갱신한다는 뜻이 아니다. `INSERT IGNORE`는 일부 오류를 경고로 처리할 수 있으며 `REPLACE`는 충돌 시 삭제 후 삽입 의미를 가지므로 일반 UPDATE처럼 취급하지 않는다.

### 복습 질문

1. 외래키 열을 선언하면 자동으로 NOT NULL과 UNIQUE도 적용되는가?
   답: 아니다. 참조 무결성과 NULL 허용 여부, 중복 허용 여부는 별개의 제약이다.
2. CHECK(price >= 0)만으로 가격의 NULL까지 막을 수 있는가?
   답: 아니다. NULL도 금지하려면 NOT NULL을 함께 지정해야 한다.

## Part 7. 트랜잭션, 격리 수준, MVCC와 잠금

### 1. ACID와 작업 경계

| 성질 | 의미 |
| --- | --- |
| 원자성 | 작업 전체를 반영하거나 실패한 작업의 변경을 되돌림 |
| 일관성 | 트랜잭션이 정한 무결성 규칙을 보존하도록 동작 |
| 격리성 | 동시 실행 간 관측과 간섭을 정해진 수준으로 제어 |
| 지속성 | 커밋한 결과를 장애에도 보존하도록 관리 |

DB 제약조건과 올바른 업무 로직이 함께 일관성을 지킨다. 트랜잭션을 선언했다고 잘못 작성한 업무 규칙이 자동으로 고쳐지지 않는다.

START TRANSACTION으로 명시적 작업을 시작하고 성공하면 COMMIT, 실패하면 ROLLBACK한다. SAVEPOINT는 전체 작업 중 일부를 되돌릴 위치이며 COMMIT은 아니다. autocommit이 켜져 있어도 명시적 트랜잭션으로 여러 문장을 묶을 수 있다.

MySQL의 일반적인 CREATE, ALTER, DROP, TRUNCATE 같은 DDL은 암묵적 커밋을 일으킨다. DML과 한 묶음으로 실행한 뒤 ROLLBACK하면 모든 것이 복구된다고 가정하지 않는다. 임시 테이블 등의 예외가 있으므로 정확한 명령 단위로 확인한다.

### 2. 읽기 이상 현상과 일반 격리 수준

| 현상 | 같은 트랜잭션에서 보이는 문제 |
| --- | --- |
| Dirty Read | 다른 트랜잭션의 미커밋 변경을 읽음 |
| Non-repeatable Read | 같은 행을 다시 읽을 때 다른 트랜잭션이 커밋한 변경을 관측 |
| Phantom Read | 같은 조건으로 다시 조회할 때 대상 행 집합이 달라짐 |

일반적인 격리 수준 설명에서 READ UNCOMMITTED는 Dirty Read를 허용한다. READ COMMITTED는 Dirty Read를 막지만 반복 조회의 변화가 가능하다. REPEATABLE READ는 반복 행 읽기의 일관성을 높인다. SERIALIZABLE은 직렬 실행과 동등한 결과를 보장하는 가장 강한 수준이다. 실제로 모든 작업을 한 스레드로 실행한다는 뜻은 아니다.

일반 이론에서 REPEATABLE READ의 phantom 가능성을 배웠더라도 이를 InnoDB의 모든 SELECT에 그대로 적용하지 않는다. 엔진, 격리 수준, 읽기 종류와 조건을 함께 봐야 한다.

### 3. InnoDB의 MVCC

MVCC는 여러 버전 중 현재 읽기에 보이는 버전을 선택하는 방식이다. Undo 기록과 Read View를 이용해 일관된 읽기를 제공한다.

- READ COMMITTED의 일반적인 비잠금 일관 읽기는 읽기마다 새 스냅샷을 사용한다.
- REPEATABLE READ의 일반적인 비잠금 일관 읽기는 같은 트랜잭션의 첫 일관 읽기에서 만든 스냅샷을 재사용한다. 자신의 변경은 별도로 보인다.
- START TRANSACTION을 호출한 순간과 첫 일관 읽기 순간을 항상 같은 시점으로 가정하지 않는다.
- UPDATE나 잠금 읽기는 일반 스냅샷 읽기와 다르게 동작한다. 둘을 섞은 결과는 각 문장 유형을 구분해서 추적한다.

### 4. 잠금과 교착 상태

| 종류 | 목적 |
| --- | --- |
| FOR SHARE | 읽은 대상의 공유 잠금을 요청 |
| FOR UPDATE | 수정 예정 대상의 배타 잠금을 요청 |
| Record Lock | 인덱스 레코드를 잠금 |
| Gap Lock | 인덱스 값 사이의 간격에 대한 삽입을 제어 |
| Next-Key Lock | 레코드와 그 앞 간격을 함께 잠금 |

InnoDB의 REPEATABLE READ에서 범위를 잠그는 조회는 Next-Key Lock을 활용할 수 있다. 존재하는 고유키를 정확히 찾는 경우 등에서는 범위 잠금과 다르게 동작한다. 인덱스와 조건이 없으면 잠금 범위도 단정할 수 없다.

배타 잠금이 걸렸다고 모든 일반 SELECT가 막히는 것은 아니다. MVCC를 사용하는 비잠금 읽기는 이전에 커밋된 버전을 읽을 수 있다. 충돌하는 쓰기나 잠금 읽기와 구별한다.

교착 상태는 서로의 잠금을 기다리는 순환이다. 공통된 자원 접근 순서와 짧은 트랜잭션으로 가능성을 줄인다. 탐지 후 한 트랜잭션이 롤백될 수 있으므로 애플리케이션은 정해진 재시도 정책을 갖춰야 한다. 재시도할 때 중복 업무가 실행되지 않는지도 검토한다.

### 복습 질문

1. SAVEPOINT까지 되돌리면 그 앞 변경은 이미 커밋된 것인가?
   답: 아니다. 그 앞 변경은 같은 트랜잭션 안에 남아 있고 아직 COMMIT되지 않았다.
2. FOR UPDATE로 잠근 행은 다른 연결의 일반 SELECT가 언제나 읽을 수 없는가?
   답: 아니다. InnoDB의 비잠금 일관 읽기는 MVCC에 따라 보이는 이전 버전을 읽을 수 있다.

## Part 8. 인덱스와 실행 계획

### 1. 빠른 탐색과 유지 비용

인덱스는 필요한 행을 찾기 위한 별도 탐색 구조다. 조회를 줄일 수 있지만 공간과 INSERT·UPDATE·DELETE 시 유지 비용이 생긴다. 결과로 읽을 행이 많으면 전체 스캔이 더 유리할 수도 있다. 특정 백분율을 보편적인 경계값으로 외우지 않는다.

B+Tree 계열 구조는 내부 노드로 탐색 범위를 좁히고 정렬된 리프를 따라 범위를 읽는 데 적합하다. 아래는 값이 저장되는 리프와 탐색 경로를 설명하는 간략도이며 실제 페이지 배치나 분할 규칙을 나타내지는 않는다.

```text
             [경계 키]
             /       \
       [낮은 범위]   [높은 범위]
            |             |
         [리프 A] <----> [리프 B]
```

### 2. InnoDB의 두 구조

| 구조 | 리프에 담는 핵심 정보 | 주의점 |
| --- | --- | --- |
| 클러스터드 인덱스 | 키와 행 데이터 | 테이블당 하나. 보통 기본키 사용 |
| 보조 인덱스 | 인덱스 키와 클러스터드 키 | 나머지 열이 필요하면 클러스터드 인덱스를 다시 탐색할 수 있음 |
| 커버링 조회 | 필요한 열을 인덱스에서 모두 얻음 | 특정 쿼리와 인덱스의 관계이며 별도 고정 인덱스 종류는 아님 |

명시적 기본키가 없으면 적합한 NOT NULL UNIQUE 인덱스를 사용하고, 그것도 없으면 내부 식별자를 만든다. 키 순으로 구조화되어 있어도 ORDER BY 없는 SELECT의 출력 순서를 보장하는 것은 아니다.

### 3. 복합 인덱스

`(category, price)`는 category를 먼저, 같은 category 안에서 price를 기준으로 정렬한 구조로 이해한다. 선행 열의 동등 조건과 뒤 열의 범위 조건을 함께 사용하는 조회에 적합할 수 있다.

```sql
CREATE INDEX idx_item_category_price
ON item (category, price);
```

- `(a, b)`와 `(b, a)`는 다른 인덱스다. WHERE에 조건을 적은 문자 순서와 인덱스 열 순서는 다르다.
- 선행 열을 건너뛴 조건은 보통 같은 방식으로 탐색 범위를 줄이지 못한다. Skip Scan이나 인덱스 전체 스캔 같은 선택이 있으므로 절대로 사용 불가라고 일반화하지 않는다.
- 열에 함수를 적용하거나 형 변환이 생기면 일반 인덱스의 범위 탐색이 어려워질 수 있다. 함수 기반 인덱스 등 별도 조건과 구분한다.
- 조건뿐 아니라 ORDER BY, 필요한 출력 열, 선택도, 쓰기 빈도를 함께 본다.

### 4. 실행 계획

EXPLAIN은 실행 계획과 추정치를 확인하는 도구다. EXPLAIN ANALYZE는 지원되는 문장을 실제로 실행하고 관측한 시간과 행 수를 제공한다. 단순한 설명 출력으로 생각해 무거운 쿼리를 무심코 실행하지 않는다.

실행 계획에서는 사용할 수 있는 인덱스와 실제 선택된 인덱스, 접근 방식, 예상 행 수, 추가 필터를 함께 본다. `key`에 이름이 있다는 사실만으로 효율적이라고 결론 내리지 않는다. INVISIBLE 인덱스는 기본적으로 옵티마이저의 선택에서 제외하지만 유지 비용은 남아 있다.

### 복습 질문

1. 보조 인덱스에 필요한 열이 모두 있으면 어떤 추가 작업을 줄일 수 있는가?
   답: 행의 나머지 데이터를 얻기 위한 클러스터드 인덱스 재탐색을 줄일 수 있다. 커버링 조회에 해당한다.
2. WHERE의 조건 순서를 바꾸면 복합 인덱스의 열 순서도 바뀌는가?
   답: 아니다. 인덱스를 정의한 열 순서는 그대로이며 옵티마이저가 조건을 분석한다.

## Part 9. 모델링, 키, 관계와 정규화

### 1. 요구사항을 테이블로 바꾸는 과정

| 단계 | 확인할 것 | 산출물 |
| --- | --- | --- |
| 요구사항 분석 | 저장할 사실, 업무 규칙, 조회·변경 작업 | 요구사항과 업무 규칙 |
| 개념 모델링 | 엔티티, 속성, 관계와 참여 조건 | 개념 ERD |
| 논리 모델링 | 키, 외래키, 관계 테이블, 종속성 | 관계 스키마 |
| 물리 모델링 | DBMS별 자료형, 인덱스, 제약과 저장 방식 | DDL과 물리 모델 |

엔티티는 지속적으로 관리할 대상이다. 속성은 그 대상의 특성이고 관계는 대상 사이의 업무 규칙이다. 현재 데이터에 우연히 중복이 없다는 이유만으로 후보키를 정하지 않는다.

### 2. 키와 관계

| 용어 | 의미 |
| --- | --- |
| 슈퍼키 | 행을 유일하게 구분하는 속성 집합 |
| 후보키 | 유일성을 유지하면서 불필요한 속성을 뺀 최소 슈퍼키 |
| 기본키 | 후보키 중 대표로 선택한 키 |
| 대체키 | 기본키로 선택하지 않은 후보키 |
| 복합키 | 둘 이상의 속성으로 구성한 키 |
| 대리키 | 업무 속성 대신 식별용으로 부여한 인위적 키 |

회원과 예약의 관계가 1:N이면 예약에 회원 참조를 둔다. 예약이 회원에 반드시 소속되는지는 외래키의 NULL 허용과 업무 규칙으로 나타낸다. 회원이 아직 예약하지 않았을 가능성과 예약에 회원이 없을 가능성은 서로 다른 방향의 참여 조건이다.

N:M 관계는 연결 엔티티로 풀어낸다. 예를 들어 수강은 학생과 강좌를 연결하며 등록일 같은 관계의 속성도 담는다.

```text
학생 (1) ─── (N) 수강 (N) ─── (1) 강좌
                 학생ID FK
                 강좌ID FK
                 등록일
```

한 학생이 같은 강좌를 한 번만 들을 수 있다면 두 ID 조합을 유일하게 만든다. 재수강을 허용한다면 학기나 수강 회차를 포함하는 식별 규칙이 필요하다. 도식의 선만 보고 규칙을 정하지 않는다.

### 3. 함수적 종속과 정규화

X가 같으면 Y도 하나로 정해지는 규칙을 `X -> Y`로 쓴다. 정규화는 이 종속성을 바탕으로 중복과 삽입·갱신·삭제 이상을 줄이는 과정이다.

다음 기록에서 `(등록번호, 강좌코드)`가 후보키라고 가정한다.

| 속성 | 업무 규칙 |
| --- | --- |
| 등록번호 | 신청 학생을 결정 |
| 강좌코드 | 강좌 이름을 결정 |
| 등록번호와 강좌코드 | 해당 신청의 수강료를 결정 |
| 학생번호 | 학생 이름을 결정 |

- 1NF: 각 속성에 원자적인 값을 둔다. 한 칸에 강좌코드 여러 개를 나열하지 않는다.
- 2NF: 1NF를 만족하고 비주요 속성이 후보키의 일부에만 의존하는 부분 종속을 제거한다. 등록정보와 강좌정보를 따로 두고 수강료는 조합에 남긴다.
- 3NF: 대표적인 위반인 비키 속성을 거치는 이행 종속을 제거한다. 등록번호로 학생번호를 알고 다시 학생 이름을 알 수 있다면 학생 정보는 별도 학생 테이블로 분리한다.

여기서 주요 속성은 어떤 후보키에라도 포함되는 속성이다. 3NF의 정확한 기준은 비자명한 함수적 종속 `X -> A`마다 X가 슈퍼키이거나 A가 주요 속성인 것이다. 기본키 하나만 보고 모든 종속성을 판정하지 않는다.

분리 후에는 필요한 사실을 손실 없이 조합할 수 있는지, 키·외래키·유일성 제약으로 업무 규칙을 표현했는지 확인한다. 정규화가 모든 조회를 빠르게 만드는 것은 아니다. 역정규화는 측정된 조회 요구와 중복 갱신 비용을 고려하는 설계 선택이다.

### 복습 질문

1. N:M 관계를 두 테이블의 외래키 하나만으로 표현하기 어려운 이유는?
   답: 한 행이 상대편 여러 행과 연결되는 사실을 개별적으로 저장해야 하므로 보통 연결 테이블이 필요하다.
2. 기본키와 후보키의 차이는 무엇인가?
   답: 후보키는 최소성을 갖는 유일 식별자이고 기본키는 그중 대표로 선택한 하나다.

## Part 10. JDBC와 백엔드 연결

### 1. API의 역할

JDBC는 Java에서 DB에 접근하기 위한 표준 API다. DBMS별 드라이버가 실제 통신을 담당한다. JDBC API와 MySQL Connector/J를 같은 것으로 보지 않는다.

| 구성 요소 | 역할 |
| --- | --- |
| DriverManager·DataSource | DB 연결 획득 |
| Connection | 연결과 트랜잭션 경계 관리 |
| Statement | SQL 실행 |
| PreparedStatement | 매개변수 자리를 가진 SQL 준비와 값 바인딩 |
| CallableStatement | 저장 프로시저 호출 |
| ResultSet | 조회 결과 순회 |

ResultSet 커서는 처음에 첫 행의 앞에 있다. `next()`가 true를 돌려준 뒤 현재 행의 값을 읽는다. JDBC의 열 위치와 PreparedStatement 매개변수 위치는 1부터 시작한다.

### 2. 값 바인딩과 실행 메서드

| 메서드 | 일반적인 용도 | 반환 |
| --- | --- | --- |
| executeQuery | SELECT 조회 | ResultSet |
| executeUpdate | INSERT·UPDATE·DELETE | 영향받은 행 수. 결과 집합을 반환하지 않는 DDL 등은 0 |
| execute | 다양한 결과 형태 | 첫 결과가 ResultSet인지 여부 |

PreparedStatement의 `?`는 값을 바인딩하는 자리다. 테이블명이나 정렬 방향 같은 SQL 구조를 임의로 바인딩하는 자리가 아니다. 동적인 식별자는 허용 목록으로 선택한다. 값을 SQL 문자열에 이어 붙이는 대신 바인딩하면 값이 SQL 구문으로 해석되는 문제를 줄일 수 있다.

준비된 문장을 쓴다고 모든 드라이버가 항상 서버에서 한 번만 컴파일하고 무조건 더 빠른 것은 아니다. 드라이버 설정과 재사용 방식에 따라 달라진다.

### 3. JDBC 실행 흐름

```text
연결 얻기
  -> SQL 준비
  -> setInt / setString 등으로 값 바인딩
  -> executeQuery 또는 executeUpdate
  -> 결과 처리
  -> ResultSet, Statement, Connection 정리
```

try-with-resources는 선언한 자원을 역순으로 닫는다. 결과가 없거나 중간에 예외가 발생해도 자원을 정리해야 한다. Connection을 쓰지 않는 다른 요청까지 공유하도록 서블릿 필드에 보관하는 방식은 피한다.

### 4. Service와 DAO 사이의 트랜잭션

주문 생성과 재고 차감이 하나의 업무라면 같은 트랜잭션이어야 한다. DAO마다 새 연결을 열고 각각 커밋하면 업무 전체를 함께 되돌릴 수 없다.

1. Service 등 업무 경계를 관리하는 쪽에서 연결을 얻는다.
2. autocommit을 끄고 참여 DAO가 같은 연결을 사용한다.
3. 모든 작업이 성공하면 commit한다.
4. 실패하면 rollback하고 원래 실패를 상위로 전달한다. rollback 자체의 실패도 놓치지 않는다.
5. 공유·대여한 연결이면 상태 복구와 반환 규칙을 지킨다. DAO가 호출자 소유 연결을 임의로 닫지 않는다.

커넥션 풀에서 close는 보통 풀에 반환하는 동작이다. 실제 연결을 계속 새로 만드는 것과 다르다. HTTP Session, DB Connection의 세션, 트랜잭션은 서로 다른 수명과 역할을 가진다.

백엔드 요청은 Controller가 받고 Service가 업무를 처리하며 DAO가 SQL을 실행한다. JSP는 화면을 표현한다. 서버에서 DB를 변경한 뒤 redirect하는 PRG는 새로고침의 재전송을 줄이지만 DB 원자성을 대신하지 않는다.

### 복습 질문

1. executeUpdate의 반환값 1은 생성한 행의 ID인가?
   답: 아니다. 일반 DML에서 영향받은 행 수를 뜻한다. 생성 키는 별도의 API로 얻는다.
2. 두 DAO 호출을 같은 트랜잭션으로 묶을 때 중요한 것은 무엇인가?
   답: 같은 Connection과 트랜잭션 경계를 공유하고 전체 성공·실패에 맞춰 commit 또는 rollback해야 한다.

## Part 11. 시험 직전 점검

| 비교 | 한 번 더 확인 |
| --- | --- |
| WHERE와 HAVING | 행을 거르는지 그룹을 거르는지 |
| COUNT(*)와 COUNT(열) | 행 수인지 NULL 아닌 값의 수인지 |
| NULL 비교와 IS NULL | UNKNOWN을 TRUE로 착각하지 않는지 |
| ON과 WHERE | 외부 조인의 보존 행을 다시 제거하지 않는지 |
| IN과 EXISTS | 값 비교인지 행 존재인지 |
| UNION과 UNION ALL | 중복 제거 여부 |
| DELETE와 TRUNCATE와 DROP | 데이터·구조·트랜잭션 영향 |
| 일반 SELECT와 잠금 읽기 | 스냅샷 읽기와 잠금 충돌의 차이 |
| 복합 인덱스의 열 순서 | 선행 열 조건과 범위 축소 가능성 |
| 2NF와 3NF | 부분 종속인지 이행 종속인지 |
| executeQuery와 executeUpdate | ResultSet인지 행 수인지 |
| HTTP Session과 Connection | 웹 사용자 상태와 DB 연결의 차이 |

### 풀이 체크리스트

- [ ] DBMS와 버전, 엔진, NULL 허용, PK·FK를 확인했다.
- [ ] SQL 결과는 각 단계에서 남는 행을 추적했다.
- [ ] 중복, NULL, 빈 결과, 미매칭 행을 확인했다.
- [ ] 정렬 기준과 동점 처리 없이 출력 순서를 단정하지 않았다.
- [ ] 트랜잭션의 연결, 실행 순서, 커밋 시점을 구분했다.
- [ ] 인덱스와 격리 수준을 조건 없는 절대 규칙으로 외우지 않았다.
- [ ] JDBC에서 값 바인딩, 결과 읽기, 예외와 자원 정리를 확인했다.
